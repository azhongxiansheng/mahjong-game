## 架构设计

### 系统整体流程

```
Player
  ↓
NetworkClient (发送消息)
  ↓
WebSocket
  ↓
GameServer (接收消息)
  ↓
GameRoom (处理消息)
  ↓
更新游戏状态
  ↓
广播给所有玩家
  ↓
NetworkClient (接收消息)
  ↓
Player UI 更新
```

### 消息类型层级

```
NetworkMessage.MessageType
├── 连接相关 (LOGIN, LOGOUT, PING)
├── 房间相关 (JOIN_ROOM, ROOM_STATE)
├── 游戏相关 (GAME_START, PLAYER_ACTION)
└── 其他 (ERROR, ACK)
```

### 房间状态机

```
WAITING → READY → PLAYING → FINISHED → CLOSED
  ↓
(玩家加入)    (房间满)  (游戏进行)   (游戏结束)
```

## 核心概念

### 1. 消息驱动架构
- 所有玩家操作都转换为消息
- 服务器接收、验证、转发消息
- 保证所有客户端同步

### 2. 房间模型
- 将游戏分离为独立的房间
- 每个房间有自己的游戏状态
- 支持多个并发游戏

### 3. 玩家管理
- 玩家通过 ID 唯一识别
- 追踪玩家所在房间
- 管理玩家的手牌

### 4. 状态同步
- 基于消息的状态更新
- 每个状态变化都是一条消息
- 确保一致性

## 技术栈

```
通信层：WebSocket（Godot WebSocketPeer）
数据格式：JSON
消息队列：FIFO 队列
编程范式：消息驱动 + 信号系统
```

## 关键设计决策

### ✅ 为什么选择 JSON？
- 易于调试
- 人类可读
- Godot 原生支持
- 跨平台兼容

### ✅ 为什么是消息队列？
- 异步处理消息
- 防止消息丢失
- 解耦消费者
- 易于扩展

### ✅ 为什么分离 GameRoom？
- 隔离不同游戏的状态
- 支持多个并发游戏
- 简化逻辑
- 易于扩展

## 使用流程

### 玩家连接流程

```
1. 创建 NetworkClient
   client = NetworkClient.new("ws://server:8080")
   
2. 连接到服务器
   client.connect_to_server(player_id, player_name)
   
3. 连接成功 → 自动发送 LOGIN 消息
   
4. 收到 ROOM_STATE 消息 → 房间信息
   
5. 等待游戏开始或手动加入房间
```

### 游戏进行流程

```
1. 服务器创建房间
   room = server.create_room(4)
   
2. 玩家加入房间
   server.player_join_room("player_1", "room_0001")
   
3. 房间满后自动准备
   room.room_state = RoomState.READY
   
4. 开始游戏
   server.start_game_in_room("room_0001")
   
5. 玩家执行操作
   client.send_message(NetworkMessage.create_discard_card(...))
   
6. 服务器处理并广播
   server.process_player_action(...)
   server.broadcast_message(...)
   
7. 所有玩家收到状态更新
```
