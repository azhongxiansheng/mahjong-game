## 2. 本轮关闭的 P2+ 问题

### 2.1 快照严格恢复与确定性

- 新增 `AuthorityReplaySnapshot.can_restore()`，LocalLoopbackServer 在领域 mutation 前完成恢复预检。
- 顶层、四席、牌墙、Momentum、技能、事件、窗口、pending kan、replay 与 AI 使用完整 exact schema/type 校验，禁止 `int()/bool()/str()` 静默强转。
- 牌墙游标必须满足非负、岭上次数 `0..4`、`draw_index + dead_size <= 136`，且 `live == 136 - draw_index - dead_size`。
- `momentum_total` 必须等于五项 score 的确定性重算值；属性键必须是 `"0".."4"` 的 canonical 字符串，拒绝 `"00"` 等别名。
- 非空技能 `hook_path` 必须存在且能加载为 `GDScript`，避免恢复时静默丢 hook。
- `window.responded`、`context.allowed_kinds` 等派生字段必须与重建窗口完全一致，避免 restore 成功但 recapture 哈希变化。
- 真实 `TileSkillFactory` 虚拟牌锚点参与发布失败回滚并支持同 `command_id` 重试。

### 2.2 Loopback 事务原子性

- 所有 accepted-action 失败路径统一进入 `_rollback_transaction()`。
- 只有权威 controller 恢复成功后才回退 `server_seq`、四席 journal 与 command cache。
- 快照可 hash 但不可恢复时，在 `apply_action` 和事件发布前返回 `EVENT_PUBLISH_FAILED`，领域状态零变化。
- restore 自身失败时设置不可复位 `_rollback_failed`；后续 `start()`、`publish_snapshot()` 和 `submit_action()` 全部拒绝，实例只能丢弃重建。

### 2.3 决策窗口性能回归

最终全量曾触发真实性能 Red：50 局 `BattleController.run_to_end` 为 5060ms，单独复跑出现 4945–7555ms；`origin/main` 同机基线为 2617ms。

根因是同一 DecisionContext 的已验证 offers 在窗口存储、读取和 `allows()` 中被重复归一化。修复没有放宽 5000ms 门槛：

- DecisionWindow 对已由 `DecisionContext.make()` 校验的 context 只做内部深拷贝，不再重复解析。
- `allows()` 只归一化调用方 payload，直接和已验证、已归一化的内部 option 比较。
- 深拷贝与收件人隔离契约保持不变。

修复后连续三次为 3305ms、3448ms、3423ms，最终全量性能预算通过。
